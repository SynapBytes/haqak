## 1. Overview

Haqak's edge functions rely on two categories of cryptographic secrets:

| Secret | Purpose | Rotation impact |
|--------|---------|----------------|
| **Supabase JWT Secret** | Signs all user session tokens | All active sessions are invalidated on rotation |
| **EMAIL_CODE_HMAC_SECRET** | Signs stored email-verification codes | Any in-flight email verification codes become invalid |
| **SUPABASE_SERVICE_ROLE_KEY** | Admin-level DB operations from edge functions | Must be updated in all function secrets simultaneously |

Secrets are resolved by the shared utility
`supabase/functions/_shared/secrets.ts` using this priority order:

```
Supabase Vault (primary, encrypted, rotatable without redeployment)
  ↓ fallback
Environment variables (Deno.env / supabase secrets)
```

## 4. Supabase JWT Secret Hardening

The JWT secret is managed entirely by Supabase — Haqak code does not generate
or store it.  However, if you suspect the secret is weak or compromised:

### 4.1 Validate current JWT secret strength

1. Go to **Supabase Dashboard → Project Settings → API**
2. Under **JWT Settings**, click **Reveal JWT secret**
3. Verify it is at least 32 characters and not a default/placeholder value

### 4.2 Rotate the JWT secret (invalidates all sessions)

> ⚠️  All logged-in users will be signed out.  Schedule during low-traffic hours.

1. **Supabase Dashboard → Project Settings → API → JWT Settings**
2. Click **"Generate new secret"**
3. Copy the new secret immediately
4. Click **"Save"**
5. All existing JWT tokens are now invalid; users must sign in again
6. Update any downstream systems that validate JWTs independently

### 4.3 Post-rotation checklist

- [ ] Verify sign-in works end-to-end
- [ ] Smoke-test the edge functions (`curl` examples in §8)
- [ ] Check error-monitoring dashboards for auth failures
- [ ] Notify users of forced re-login if necessary

## 5. Supabase Vault Setup

Vault stores secrets encrypted at rest and allows rotation without redeploying
edge functions (the 5-minute TTL cache in `secrets.ts` picks up new values
automatically).

### 5.1 Enable Vault integration

```bash
# Store EMAIL_CODE_HMAC_SECRET in Vault
supabase vault add --name EMAIL_CODE_HMAC_SECRET \
  --value "$(openssl rand -hex 32)" \
  --project-ref <YOUR_PROJECT_REF>

# Optionally store other secrets
supabase vault add --name AUDIT_HMAC_KEY \
  --value "$(openssl rand -hex 32)" \
  --project-ref <YOUR_PROJECT_REF>
```

### 5.2 Grant edge functions access

The `service_role` already has `SELECT` on `vault.decrypted_secrets` by
default in Supabase-managed projects.  If you need to verify:

```sql
-- Run in Supabase SQL Editor
GRANT SELECT ON vault.decrypted_secrets TO service_role;
```

### 5.3 Enable Vault reads in edge functions

```bash
# Tell the secret manager to use Vault
supabase secrets set SUPABASE_VAULT_ENABLED=true \
  --project-ref <YOUR_PROJECT_REF>
```

### 5.4 Verify Vault lookup works

Deploy and invoke an edge function, then check logs for the absence of
`[secrets] Required secret … is not configured` errors.

## 6. Zero-Downtime Email-Code HMAC Secret Rotation

Because verification codes are short-lived (10 minutes), you can perform a graceful
rotation with zero service interruption:

```
Step 1 – Generate new secret
Step 2 – Store new secret in Vault under a new versioned name
Step 3 – Update edge functions to check new name first, old name as fallback
Step 4 – Wait for all in-flight verification codes to expire (≤ 10 min)
Step 5 – Remove old secret from Vault
Step 6 – Remove the fallback lookup from code
```

### 6.1 Detailed steps

```bash
# 1. Generate the new secret
NEW_SECRET=$(openssl rand -hex 32)
echo "New secret (save this): $NEW_SECRET"

# 2. Store in Vault
supabase vault add --name EMAIL_CODE_HMAC_SECRET_NEW \
  --value "$NEW_SECRET" \
  --project-ref <YOUR_PROJECT_REF>

# 3. Invalidate the cache so functions pick up the new secret
#    (or wait up to 5 minutes for TTL expiry)
# No redeployment needed if SUPABASE_VAULT_ENABLED=true

# 4. Wait 10 minutes for in-flight verification codes to expire

# 5. Rename the secret in Vault
supabase vault rm --name EMAIL_CODE_HMAC_SECRET_OLD \
  --project-ref <YOUR_PROJECT_REF>

supabase vault add --name EMAIL_CODE_HMAC_SECRET \
  --value "$NEW_SECRET" \
  --project-ref <YOUR_PROJECT_REF>
```

## 7. Emergency Rotation (Compromised Secret)

Use this procedure when you have evidence a secret has been leaked.

```bash
# ─── 1. Generate replacement secrets ───────────────────────────────────────
NEW_EMAIL_CODE_HMAC=$(openssl rand -hex 32)
echo "NEW_EMAIL_CODE_HMAC_SECRET: $NEW_EMAIL_CODE_HMAC"

# ─── 2. Push to Supabase Edge Function secrets ─────────────────────────────
supabase secrets set EMAIL_CODE_HMAC_SECRET="$NEW_EMAIL_CODE_HMAC" \
  --project-ref <YOUR_PROJECT_REF>

# ─── 3. Invalidate active email verification codes in the database ────────────────────────
# Run in Supabase SQL Editor:
#   UPDATE email_verification_codes
#   SET used = true, used_at = now()
#   WHERE used = false AND expires_at > now();

# ─── 4. Rotate Supabase JWT secret (forces re-login) ───────────────────────
# Dashboard → Project Settings → API → JWT Settings → Generate new secret

# ─── 5. Update Vault entry ─────────────────────────────────────────────────
supabase vault rm --name EMAIL_CODE_HMAC_SECRET --project-ref <YOUR_PROJECT_REF>
supabase vault add --name EMAIL_CODE_HMAC_SECRET \
  --value "$NEW_EMAIL_CODE_HMAC" \
  --project-ref <YOUR_PROJECT_REF>

# ─── 6. Run health checks ──────────────────────────────────────────────────
# See §8 below.
```

> **Audit log**: After an emergency rotation, review Supabase logs for any
> anomalous auth activity in the period the secret was potentially compromised.

## 8. Health Checks & Verification

```bash
PROJECT_URL="https://<YOUR_PROJECT_REF>.supabase.co"

# 8.1 CORS preflight — both functions must return 200
curl -s -o /dev/null -w "%{http_code}" \
  -X OPTIONS \
  -H "Origin: https://haqak.app" \
  -H "Access-Control-Request-Method: POST" \
  "${PROJECT_URL}/functions/v1/request-email-verification"
# Expected: 200

curl -s -o /dev/null -w "%{http_code}" \
  -X OPTIONS \
  -H "Origin: https://haqak.app" \
  -H "Access-Control-Request-Method: POST" \
  "${PROJECT_URL}/functions/v1/verify-email-code"
# Expected: 200

# 8.2 Unauthenticated POST — must return 401, not 500
curl -s -o /dev/null -w "%{http_code}" \
  -X POST \
  -H "Content-Type: application/json" \
  -d '{}' \
  "${PROJECT_URL}/functions/v1/request-email-verification"
# Expected: 401

# 8.3 Check for weak-secret warnings in logs
supabase functions logs request-email-verification --project-ref <YOUR_PROJECT_REF> \
  | grep weak_secret_detected
# Expected: no output
```

## 9. Monitoring & Alerts

Set up the following alerts in your observability platform:

| Alert | Condition | Severity |
|-------|-----------|----------|
| Weak secret detected | `weak_secret_detected` in function logs | Critical |
| Auth error spike | >5% of requests return 401 within 5 min | High |
| verification-code failure rate | >10 failed verification attempts / min | High |
| JWT expiry cluster | Unusual volume of 401s from valid users | Medium |

Example Supabase log filter (Logflare / Grafana):
```
event = "weak_secret_detected"
```

### Secret rotation reminder

Schedule quarterly rotations by creating a calendar event or GitHub issue.
A stale-secret CI check (`.github/workflows/secret-rotation-check.yml`) runs
weekly and will open an issue if it detects placeholder values checked in.

## 10. Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `500 Server configuration error` after rotation | New secret not picked up yet | Wait for 5-min cache TTL or redeploy |
| All verification codes rejected after rotation | verification codes signed with old secret | Expected; users must request a new verification code |
| `weak_secret_detected` in production logs | Placeholder value deployed | Rotate immediately using §6 or §7 |
| Vault lookup fails silently | `SUPABASE_VAULT_ENABLED` not set | Set the env var and redeploy |
| Users forcibly logged out | JWT secret was rotated | Normal behaviour; inform users |
